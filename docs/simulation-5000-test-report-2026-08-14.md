## 3. 积压特征

### 3.1 启动突发

- 15,000 Tick/秒启动突发期间，待处理加处理中峰值约 20.7 万条；
- 突发结束后持续输入仍为约 5,000 Tick/秒；
- 约 134 秒时首次追平到数百条以内；
- 证明恢复吞吐高于稳态输入，但持续 15,000 Tick/秒不属于当前单机稳定容量。

### 3.2 稳态周期性停顿

稳态阶段多次出现约 3～6 万条短时积压，通常在 20～50 秒内恢复到数百条。期间没有 rejected 或 expired，但这种周期性抖动不能视为完全通过。

优先排查：

1. 100 个 Python 子进程的 Windows 调度竞争；
2. Python GC 或多进程同时执行批量提交；
3. SQLite WAL checkpoint/fsync 同步峰值；
4. 50 个 Relay 同时刷新和 gRPC 批量 ACK；
5. Redis Lua 调用、Redis fork/持久化或 Docker/WSL2 调度；
6. OpenTelemetry/Prometheus 周期采集是否与停顿周期重合。

## 4. 测试停止情况

- 按 `run_id` 精确定位主进程；
- 终止整个模拟进程树；
- 50 个模拟生产进程、50 个 Relay 和父进程均已退出；
- 复核带该 `run_id` 的 Python 进程数为 0；
- AStockMonitor.Api、AStockMonitor.Worker、AStockMonitor.StrategyScanner 仍为 Running/Automatic；
- Grafana 等运维容器未停止。

由于测试是按要求强制停止，不是模拟器自然结束，因此没有生成最终 `result.json` 和排空后的延迟分位报告；只保留了 `manifest.json`、终端采样和 Redis/SQLite 中具有测试标识的数据。

测试 Outbox 可能保留停止瞬间的 `pending/in_flight` 审计记录；Redis 中 `LOAD.*` 测试数据按 Tick V3 TTL 和 Stream 上限自然释放。不能直接删除整个当日 V3 分片键，因为同一键可能同时包含正式证券数据。

## 5. 当前判定

| 验收项 | 判定 |
|---|---|
| 5,000 Tick/秒平均吞吐 | 阶段通过 |

| 15,000 Tick/秒持续能力 | 未通过；仅可承受短时突发 |
| 稳态延迟一致性 | 未通过；存在周期性积压 |

结论：当前 Tick V3 单机链路可以承载约 5,000 Tick/秒平均输入，但还不能宣称“5,000 股票生产验收通过”。下一次测试应先降低进程数或实现 Relay 池化，同时采集分阶段耗时和主机资源，定位周期性停顿后再执行完整 30 分钟测试。
